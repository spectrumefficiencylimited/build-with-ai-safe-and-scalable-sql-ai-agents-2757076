Enabling fallback options: Defining a fallback model system
Let's talk about model fallback strategy. Specifically, what is a model fallback strategy, when should we use it, and how do we select models? Let's start with the what. In the previous lesson, we saw how the debugger agent successfully fixed an invalid SQL query in a single iteration. In practice, that won't always happen. Sometimes the agent needs multiple attempts to identify and resolve an issue. But what if it keeps failing? To avoid endless loops, we first need to set a maximum number of iterations. More importantly, we need a fallback plan, a way to recover when the primary model cannot solve the problem. A model fallback strategy is simply a plan B. You can think of it as an escalation path for cases where the debugger agent fails to resolve the issue using the default model. So when do we use it? When the primary model fails after the allowed number of iterations, we retreat the task using a more capable model. The goal is to improve the chances of success without defaulting to the most expensive model every time. And this is where the strategy comes into play as choosing a primary model is usually a balance between performance and cost. More powerful models tend to be more expensive and the best model is not always the most cost-effective choice. A common approach is to select a primary model that handles most everyday cases well and then use a stronger model as a fallback for other or more ambiguous scenarios. How do we choose the models? One simple way is to define a set of unit tests and run them across different models. Based on their performance, you can measure each model's coverage and decide which one should be your default and which one should be a fallback.
