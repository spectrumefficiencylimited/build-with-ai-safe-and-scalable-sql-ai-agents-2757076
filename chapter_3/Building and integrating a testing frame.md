Building and integrating a testing framework
So far, we've explored the core components of a SQL AI agent, from prompt templates to error handling. One of the final steps before deploying an agent to production, it's testing its functionality and performance. In this lesson, we'll work through an example of testing framework that focuses on two key scenarios. End-to-end evaluation of the agent's ability to answer user questions and evaluation of the debugger agent's ability to fix errors during runtime. Although our focus here is module evaluation, the same principles apply to other parts of the system, such as prompt handling and safety validation. You can use this approach as a foundation and extend it to cover the agent's core components. For this demo, we'll use the 0404B Jupyter Notebook in the Chapter 4 folder. We will evaluate seven OpenAI models covering a wide range of capabilities. This includes the model we have used throughout the course, GPT-4.0, as well as more advanced models available at the time of recording, such as GPT-4.2 and smaller variants like Nano and Mini. I used Cloud Code to generate a suite of tests for the air traffic datasets. Those tests rely on the skill we introduced in chapter 2 to provide a consistent domain context. You can find them in the testing module under the SQL agent folder in the course repository. Because the tests take time to run, this notebook has been pre-rendered. The first group of tests includes 20 questions organized by difficulty level and SQL functionality. Those tests cover aggregation, comparison, complex filters and more. The second group of tests simulates broken SQL queries and evaluates the debugger agent's ability to fix them. You can see the next table with the list of queries and their difficulty and category. After defining the Postgres SQL connection and selecting the model to evaluate, we run the full suite of tests. In total, 175 tests. Let's scroll down and review the results. And here is the summary results. The summary table shows statistics for each model including the number of tests, the success rate, failure, and the execution runtime. Below that, we see a visual breakdown of the results. The left chart shows success rate of the query generation test. As expected, GPT 5.2 achieves the highest overall score. close behind are the GPT-5 Mini and Nano models. The lowest scores come from the GPT-4 Nano and Mini. In the debugging test, all models successfully resolved the simulated failures. Another important matrix is execution time. Here, GPT-5 Nano is the slowest, with an average execution time of about 24 seconds per request. In comparison, the best model in this category, GPT 4.1 nano, average execution time was under a second. It's worth noting that execution time can vary across runs, so drawing conclusions from a single test is risky. In practice, you'll want to evaluate performance across multiple samples. Finally, let's look at the success rates by question difficulty. At the left is the easy category questions, followed by the medium and hard questions on the right side. All models perform equally well on easy questions, achieving a success rate of 80%. The biggest difference appears in the medium difficulty queries. This ties directly back to the previous lessons on fallback strategies. For example, GPT-4 or perform similarly to top-tier models on both easy and hard questions that suggest limited added value in using more expensive models as default. This is exactly the type of trade-off you should consider when choosing a primary model and defining a fallback option.
