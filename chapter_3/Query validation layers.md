Query validation layers
One of the main risks when using SQL agents, as we saw in the previous lesson, is the generation of SQL queries that can alter, delete, or modify the database. This can happen when a user accidentally ask for a destructive action or when the LLM misunderstands the request and generates an unsafe query. To prevent those scenarios, we need to put strong guardrails in place. In this lesson, we'll review three simple but powerful methods that when used together help ensure the safe use of SQL agents in production environment. The first line of defense after the LLM generates the SQL query is a validation function that evaluates the query. This function allows only a restricted subset of SQL commands such as SELECT or WITH, and blocks others like DELETE, DROP, or ALTER. This function will pass the query to the DB handler if and only if it passes the validation test. Next, it is important to understand how the Python client you use to connect to the database handles SQL execution. For example, in this course, we are using IBIS as the backend query engine. The IBIS library provides two main methods to execute SQL queries. The first method called SQL, and it limited to non-mutating commands such as select or describe. If a query includes commands like delete, insert, or update, the function rises an arrow. And the second method, row underscore SQL, which allows execution of any SQL command, including those that can modify, delete, or drop database objects. Last, and the most fundamental guardrail, is the database access control. You should work with your database admin to define an access role with strict read-only permission. This ensures that even if a destructive query slips through the validation process, then the database itself will reject it. This layer of protection operates independently of the agent, and it is your last line of defense.
